# CONTENT-FORMAT.md —— 内容格式与数据管理规范

> 这份文档回答三个问题：**文件怎么存**、**JSON 长什么样**、**新词怎么进来**。
> 这是本项目的「数据契约」——UI 全部由它驱动，改它 = 改内容，不用碰组件。

---

## 0. 一句话总览

| 概念 | 位置 | 说明 |
|---|---|---|
| 词库（会持续增长） | `src/data/words.json` | 每个复合动词一条记录 |
| 系（前項/后项，很少变） | `src/data/series.json` | 横轴列（后项）与纵轴行（前项） |
| 站点设置 | `src/config.js` | 标题、页脚、赞助弹窗 |
| 设计真源 | `design/zukan.html` | 视觉唯一真源（只读参考） |

**没有后端接口。** 这是静态站点，数据在构建时打包进产物。加内容 = 编辑 JSON → 校验 → 重新部署（见 README「加一个词」）。

## 1. `src/data/series.json` —— 系（行与列）

```jsonc
{
  "rows": [                       // 前項系（矩阵的「行」）
    {
      "id": "tori",               // 唯一 id（ASCII slug），也是 URL hash `#series-tori`
      "name": "取り〜",           // 系名（显示）
      "proto": "取る",            // 原型动词
      "kan": "一只手：伸手 → 抓住 → 拿过来。获取 · 処理 · 受容三枝。",  // 语感说明（纯文本）
      "rich": "tori"              // 可选：有专属定制页的系（值 = 定制组件 id）
    }
  ],
  "cols": [                       // 後項系（矩阵的「列」）
    {
      "id": "dasu",
      "name": "〜出す",
      "proto": "出す",
      "kan": "向外 · 出来。"
    }
  ],
  "seriesNames": {                // 可选：显式系名覆盖（一般不写，名称自动派生）
    "yugo": "融合系"
  }
}
```

**规则：**
- `id` 必须小写 ASCII，与 `words.json` 里词条的 `row` / `col` / `series` 引用一致。
- 新加一个系，**不用改任何组件**——它会自动获得通用系页（成员墙 + 系内小地图 + 空槽统计）。只有想给它配专属的叙事页（像 tori / kaesu / komu 那样）才需要加组件。
- `seriesNames` 通常不需要：`yugo` 是内置特殊系（融合），其余名称自动 = `name + '系'`。

## 2. `src/data/words.json` —— 词库

外层是一个 `words` 对象，**key = 词条 id**（也是 URL hash，如 `#kangaekomu`）：

```jsonc
{
  "words": {
    "kangaekomu": { /* 词条 */ },
    "torimodosu": { /* 词条 */ }
  }
}
```

每个词条有两种**形态**（`status` 字段区分），字段集合不同：

### 形态 A：`collected` —— 収蔵済 · 完整标本卡（「标本」）

卡片会展示：標本编号 / 朱印 / 可导出性★ / 构词分类 / 语源解剖 / 近缘词族 / 商务+IT 用例 / 语感口诀。

```jsonc
{
  "id": "kangaekomu",            // ① 必填，与 key 一致，ASCII slug
  "word": "考え込む",            // ① 必填 词面
  "reading": "かんがえこむ",     // ① 必填 假名读音
  "romaji": "kangae-komu",       // ② 罗马字（建议填）
  "row": "kangae",               // ① 必填 前項系 id（融合词为 null）
  "col": "komu",                 // ① 必填 后项系 id（融合词为 null）
  "status": "collected",         // ① 必填 固定 "collected"
  "series": "komu",              // ① 必填 归属系（行 id / 列 id / "yugo"）
  "no": "03",                    // ① 必填 标本编号（两位字符串）
  "seal": "込",                  // ① 必填 朱印一字（取自核心词义）
  "stars": 4,                    // ① 必填 可导出性 1–5（前项+后项能否推出词义）
  "cls": "④",                    // ① 必填 构词分类：①②③④⑤ 之一
  "clsNote": "後項の接尾辞化",    // ① 必填 分类说明（日文）
  "genus": "〜込む系 · 深陷内心",  // ① 必填 属（系 · 分支）
  "pos": "五段動詞",              // ① 必填 品詞
  "tagline": "想着想着，整个人栽了进去 —— <b>深思 · 想得入神</b>",  // ① 必填 一句话展示语（可含 <b>）
  "core": "核心イメージ：<b>思考「栽」进了深处，拔不出来</b> —— 深く考える・没頭する。",  // ① 必填 核心イメージ（可含 <b>）
  "eq": {                        // ① 必填 语源解剖
    "front": "考え",             //   前项
    "frontSrc": "〈考える〉",      //   前项原型（带 〈〉，显示时自动去括号）
    "frontNote": "思考",         //   前项含义（中文）
    "back": "込む",              //   后项
    "backRole": "後項 · 接尾辞",  //   后项角色标签
    "backNote": "深入 · 完全 · 沉浸",  // 后项含义
    "backShift": "<b>意味転換</b> 「进入」→「彻底陷入」",  // ③ 可选 后项语义转换说明（可含 HTML）
    "result": "考え込む",        //   合成词
    "resultNote": "沉思 · 想得入神",  // 合成词含义
    "resultShift": "<b>語義分岐</b> …"  // ③ 可选 合成词语义分岔（可含 HTML）
  },
  "families": [                  // ① 必填 近缘词族（至少一组）
    {
      "title": "同後項「〜込む」· 深陷内心系",  // 组标题
      "sub": "心思栽进去出不来",              // 组副标
      "items": [                              // 每组最多 6 个词，[词面, 中文释义, 是否本种?]
        ["思い込む", "深信"],
        ["考え込む", "深思 · 入神", true]     // 第三个元素 true = 本词（显示 ★ 本種）
      ]
    }
  ],
  "intersect": "<b>交差点：</b>本种是「深陷内心」分支的代表…",  // ① 必填 交叉点解说（可含 <b>）
  "usages": {                    // ① 必填 用例：商务 / IT 各 3 条 [日文, 中文]
    "biz": [
      ["会議中、彼はしばらく考え込んでから、ようやく発言した。", "会议中他沉思了好一会儿，才终于开口发言。"]
    ],
    "it": [
      ["バグの原因を特定できず、開発者は画面の前で考え込んでいた。", "因为无法定位 bug 的原因，开发者在屏幕前陷入了沉思。"]
    ]
  },
  "note": "「想着想着，整个人栽了进去——再抬头，天都黑了」",  // ① 必填 覚え方口诀
  "noteZh": "込む = 深く・すっかり。「考え込む」是深陷内心系的原型。"   // ① 必填 中文记忆说明
}
```

### 形态 B：`known` —— 既知 · 未収蔵占位卡（「认识但还没做标本」）

卡片只展示：词面 / 读音 / 中文释义 / 坐标 / 归属系 / 備忘録。

```jsonc
{
  "id": "torimodosu",            // ① 必填 与 key 一致
  "word": "取り戻す",            // ① 必填
  "reading": "とりもどす",       // ① 必填
  "row": "tori",                 // ② 建议 前項系 id（融合词省略）
  "col": "modosu",               // ② 建议 后项系 id
  "status": "known",             // ① 必填 固定 "known"
  "series": "tori",              // ② 建议 归属系
  "stars": 5,                    // ③ 可选 可导出性 1–5
  "cls": "③",                    // ③ 可选 构词分类
  "gloss": "恢复 · 夺回",         // ① 必填 中文释义
  "cat": "获取",                  // ② 建议 分类标签（获取 / 処理 / 受容 / IT / 商务…）
  "note": "前項接頭辞化 —— 「取」的本义仍可辨识…"   // ② 建议 備忘録
}
```

> ② = 建议（让格子/成员墙/系归属正确显示）；① = 必填（校验脚本会检查）。

## 3. 词条生命周期：`known` → `collected`

这是推荐的加词节奏：

```
遇见新词
   │
   ▼
① known 占位（快速入库，几秒）
   │  —— 只填必填 + 坐标，矩阵立刻亮一格淡格
   ▼
② collected 标本卡（有空了再升级）
   │  —— 用完整 Prompt 补全 eq / families / usages / 口诀
   ▼
③ 在地图上变实格（朱印点亮）
```

- `known` 升级 `collected`：把 `status` 改成 `"collected"`，补上 collected 必填字段，删掉 `gloss`/`cat`。
- `collected` 降级 `known`：反向操作。
- 两种形态并存是刻意设计——「既知」让新词先占位，图鉴永不因词卡不完整而缺失。

## 4. 加一个新词（完整步骤）

1. **判断它是哪类**：属于现有前項系 / 后项系吗？在矩阵里对应哪个交点？
   - 属于现有系 → 直接进第 3 步。
   - 出现全新系（如新的后项「〜込む」的对立面）→ 先加系（见第 5 节）。
2. **生成内容**：用 [`docs/AI-PROMPTS.md`](docs/AI-PROMPTS.md) 的 Prompt。想先快速占位用「快速 Prompt」，想一步到位用「完整 Prompt」。
3. **入库**：把 AI 返回的 JSON 粘贴到 `src/data/words.json` 的 `words` 对象里（记得 key 与 `id` 一致）。
4. **校验**：`npm run check:data`。报错就按提示修。
5. **部署**：`git push` → Vercel 自动重新部署。

**入库后自动生效**（无需改组件）：
- 矩阵对应交点点亮一格（collected = 实格朱点，known = 淡格）
- 对应系（行/列）的成员墙、系内小地图、系进度条、首页统计同步更新
- 词卡通过 `#<id>` 直接可访问

**不会自动更新**（需要手动）：
- 定制系页里的**叙事内容**（tori 语义树、kaesu 隐喻面板、komu 结构图等）是设计内容，新词不会自动出现在里面。想让新词出现在这些展示面板 → 在对应的 `src/components/series/*.jsx` 里手动加一行。
- cover 印章下的「収蔵 No.01–04」等静态文案（`src/components/Cover.jsx`）。

## 5. 加一个新的前項/后项系

```jsonc
// src/data/series.json
{
  "rows": [ /* …原有… */, { "id": "nagashi", "name": "流し〜", "proto": "流す", "kan": "流动 · 冲洗。" } ]
}
```

- 新系自动获得通用系页（`GenericSeries`）：系名片 + 系内小地图 + 成员墙 + 空槽统计，零代码。
- 想给它专属叙事页：在 `src/components/series/` 新建 `XxxSeries.jsx`，然后在 `SeriesView.jsx` 里加一行注册。

## 6. 校验工具

```bash
npm run check:data
```

校验内容：
- `series.json`：行/列 id 唯一、必填字段齐全
- `words.json`：key 与 id 一致、status 枚举、按形态的必填字段、cls 在 ①②③④⑤ 内、stars 为 1–5 整数或 null、row/col/series 引用真实存在

**建议每次改完 JSON 都跑一次**；CI 或部署前钩子也可以加上（`package.json` 里把 `check:data` 挂进 build 前）。

## 7. 未来需要「运行时更新」时的演进路径

当前阶段：**静态 JSON + 重新部署** 是最简单、零风险的方案（部署到 Vercel 自动触发）。如果以后想要「不改代码就能加词」，按成本从低到高的三条路：

1. **数据文件放 `public/`**：把 `words.json` 挪到 `public/data/`，React 用 `fetch('/data/words.json')` 加载。仍要重新部署，但不用动组件代码。（改动小，收益低）
2. **Vercel API Route**：加一个 `api/words` 端点读写 JSON，配一个只有你能访问的写入口。前端仍静态。（要引入后端逻辑与鉴权）
3. **托管数据库**：Supabase / Upstash / 云 KV。彻底动态，但要维护数据迁移、权限、费用。（收益高，成本也高）

**建议**：在词条还没超过几百条、只有你一个人维护时，用当前静态方案。等词多了、或者想开放贡献再升级。方案 2 的成本主要是维护，方案 3 成本主要是钱——文档不替你决定，时机成熟再评估。

## 8. 边界与注意事项

- **字段含 HTML**：`tagline`、`core`、`intersect`、`eq.backShift`、`eq.resultShift` 允许 `<b>` 等轻量标签（渲染用 dangerouslySetInnerHTML）。请只放自己生成的内容，不要引入用户输入。
- **id 命名**：用罗马字连字符（如 `toriireru`、`dashi_oshimi`），不要用日文假名或空格。
- **`series` 与 `row/col`**：collected 词必须三者在场；known 词 row/col 建议填（否则占位卡显示「融合帯 ⑤」位置并归入「待归档」）。
- **融合词**（`cls` ⑤，如 `落ち着く`）：`row` 和 `col` 都设为 `null`，`series: "yugo"`。
